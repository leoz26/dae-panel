# 双软路由连接稳定性测试框架（设计稿，待确认）

被测对象：**A = 192.168.1.85（dae，本项目）**，**B = 192.168.1.11（OpenWrt + OpenClash，dropbear/LuCI/9090）**。
目标不是"跑个 ping 看看"，而是回答四个问题：

1. 两条路径各自**多久断一次、断多久、断在那一层**（链路 / TCP / TLS / HTTP / DNS）。
2. 断的时候**是谁的问题**（本机探针、旁路由、机场节点、运营商 DNS）。
3. 24 小时内**能不能撑住**（长稳、内存/连接数增长、reload 影响）。
4. 出问题后**多快恢复**（MTTR），以及"换个节点/换个出口"是否更快。

---

## 0. 已核实的现场事实（2026-10-24）

| 事实 | 来源 |
|---|---|
| Mac(192.168.1.101) 默认网关 = **192.168.1.1**（不是 .11、不是 .85） | `route -n get default` |
| .11 是 OpenWrt：22 dropbear / 53 dnsmasq / 80·443 LuCI / **9090**（疑似 OpenClash API） | 端口探测 + SSH banner |
| Mac → .11 ping 3.5ms 0% loss；Mac → .85 ping 4.6ms 0% loss | `ping -c 4` |
| .85 → .11 ping 0.9ms 0% loss；.85 → .1 ping 1.1ms 0% loss | `ping -c 4` |
| .85 有 `python3`、`ping`、`ss`、`ip`，**没有 curl / strings** | `which` |
| 两台 traceroute 的 UDP/ICMP 探测都被吞（全 `*`） | 之前的 whereami.py 实测 |
| 机场对同一出口 IP 的突发重复请求会挂起（限流） | 订阅拉取 30s 超时事件 |

推论：**当前 Mac 的流量既不经过 .11 也不经过 .85**（走 .1）。所以"客户端视角"的对比必须先显式改路由/网关，属于**会影响本机上网**的操作，需要单独授权。

## 1. 分层模型（断在哪一层）

| 层 | 测什么 | 手段 | 判据示例 |
|---|---|---|---|
| L0 链路 | 丢包、抖动、RTT 分布、ARP 抖动 | ICMP `ping` 连续采样（1s×N） | p95 RTT < 10ms、丢包 0% |
| L1 TCP | SYN 成功率、建连时延、半开连接 | 非阻塞 connect + 超时 | 失败率 < 0.5%、p95 建连 < 400ms |
| L2 TLS | 握手成功率、握手时延、证书有效期/链 | ssl 握手（不校验） | 失败率 < 1% |
| L3 HTTP | 状态码、首字节、总时长、**内容校验**（防 captive portal/劫持） | 极简 HTTP/1.1 请求 + 关键字断言 | 2xx 且含期望串 |
| L4 DNS | 解析时延、A/AAAA 一致性、TTL、是否被投毒 | 直连 53 UDP，对比 .1 / .11 / 223.5.5.5 | 结果一致、p95 < 100ms |
| L5 吞吐 | 单流/多流下载速率、上传速率、是否被限速 | 定长下载（≤2MB） | 达基线 70% 以上 |
| L6 长稳 | 连接数、内存、句柄、dae 进程 RSS、OpenClash 内存 | `/proc`、`ss -s`、日志计数 | 24h 无单调泄漏 |
| L7 代理内部 | 节点切换次数、组重选、失败 dialer | dae journal、OpenClash 日志/API | 断流时段与实际切换对应 |
| L8 故障注入 | 停/启 dae、切网关、reload、断上游 | 受控操作（需授权） | 恢复 < 30s 且业务可感知 |

## 2. 探针位置（三种视角，不要混）

- **P-A**：在 .85 本机跑 → 测"A 作为旁路由时它的上游是否稳"。目标集合走 A 的出站（本机流量本来就被 dae 接管）。
- **P-B**：在 .11 本机跑（需 SSH 只读）→ 测"B 的上游是否稳"。若拿不到 SSH，只能用 9090 的 API 或从外部间接测。
- **P-C**：在 Mac（或任意 LAN 客户端）跑，分别把默认网关/DNS 指向 .85 / .11 → 测"客户端真实体感"。**会改本机网络，需授权**，且建议一次只切一条、切完立刻恢复。
- **P-D**：在 .85 上"反测"对端：ping/tcp 到 .11 的 53/80/9090，再配合 .11 的 uptime，判断**旁路由本身是否掉线**（区别于机场掉线）。

## 3. 目标集合（固定，便于横向对比）

| 类别 | 目标 | 用途 |
|---|---|---|
| 境内直连 | `www.baidu.com:443`、`223.5.5.5:443` | 基线（不应被代理） |
| 境外稳定 | `www.cloudflare.com:443`、`1.1.1.1:443` | 代理主测点 |
| 境外易断 | `www.google.com:443`、`www.youtube.com:443` | 区分"全断"与"个别站点被墙" |
| 机场敏感 | 订阅域名（`s3.dlpublicsub.com`、`link.sumno.xyz`）| 低频率（≥60s 一次），避免触发限流 |
| DNS | `.1:53`、`.11:53`、`223.5.5.5:53` | 解析对比 |

## 4. 度量与判据（先定口径，再看数）

对每个 (探针, 目标, 层) 输出：`count`、`ok`、`fail`、`failRate`、`p50/p95/p99`、`max`、`jitter`（相邻 RTT 差的标准差）。
另加三个复合指标：

- **断流事件（outage）**：同一目标连续 ≥3 次失败，或成功但耗时 > 10s → 记一次事件，含开始/结束/持续秒数/涉及层。
- **MTTR**：从事件开始到连续 3 次恢复成功的秒数。
- **稳定性评分**：`100 - failRate*100*k1 - outageMinutes*k2 - p95Excess*k3`（权重先取 k1=1, k2=2, k3=0.5，看数据再调）。

判据（建议初值，可调）：

| 指标 | 通过线 | 说明 |
|---|---|---|
| L1 建连失败率 | ≤ 1% | 超过说明路径不稳 |
| L3 HTTP 成功率 | ≥ 98% | 含内容校验 |
| 断流事件 | 1 小时内 ≤ 1 次、单次 ≤ 30s | 长稳 |
| p95 RTT（境外） | ≤ 800ms | 香港/新加坡节点正常区间 |
| DNS 一致率 | 100% | 与 223.5.5.5 对比 |

## 5. 编排与实现（零依赖优先）

```
tools/netdiag/stability/
  probe.py      # 单文件探针：python3 标准库，无第三方依赖
  analyze.py    # 汇总 JSONL → Markdown/CSV 报告（含评分、outage 表）
  run.sh        # 编排：本机/远端并行、时长控制、结果回传
  DESIGN.md     # 本文件
logs/stability/2026-10-24T2310Z/{probe-a85.jsonl, probe-b11.jsonl, report.md}
```

- **probe.py**：`--targets sets`、`--interval 10`、`--duration 3600`、`--layers l0,l1,l2,l3,l4`、`--out`、`--tag`。单进程线程池（目标数 ≤10）避免成为干扰源；全部时间戳用 **UTC epoch 秒**；每条记录一行 JSONL 便于断点续跑。
- **run.sh**：`scp probe.py` 到 .85（和 .11，如可登录）→ 远端 `nohup python3 ... &` → 本地同时跑 → 到点取回 JSONL → `analyze.py` 出报告。
- **analyze.py**：按 (探针,目标) 聚合、算 outage、按小时切窗、输出 Markdown 表 + 一行结论（"A 更稳/B 更稳/无差别"）+ 归因提示（看哪个层先失败）。

**为什么不用现成工具**：.85 没有 curl/mtr，一台装了另一台没有就没法对比；python3 单文件两边都能跑，且能把 L1/L2/L3/L4 打通成一条时间线。可选增强：如果 .11 允许装包，再补 `mtr -T -P 443` 做 TCP 路由追踪。

| 阶段 | 内容 | 时长 | 影响面 |
|---|---|---|---|

## 7. 风险与红线

1. **不改 .11 的任何配置**（OpenClash/LuCI/DHCP 都不碰），只读 API/日志；如需 SSH，只做只读命令。
2. **不高频打机场订阅域名**（≥60s/次），已有"限流→30s 超时"前科。
3. **S2 会改本机网关**：必须先记原值（`192.168.1.1`）、单次切换 ≤30 min、结束立即恢复并验证可上网；失败立刻回退。
4. **流量预算**：L5 吞吐单次 ≤2MB、每小时 ≤50MB，避免干扰真实使用与被运营商限速。
5. 探针并发 ≤10 线程、间隔 ≥5s，避免"测出来的不稳是探针自己造成的"。
6. 结果只写 `logs/stability/`，不入 git（含内部 IP 与订阅域名）。

## 9. 断网风险预案（v2 追加，2026-10-24 实测后修订）

### 9.1 风险比"改网关会断网"更严重

实测我这侧的执行前提（Mac，用户 sthho）：

| 检查 | 结果 | 含义 |
|---|---|---|
| `id -u` | 501（普通用户） | — |
| `sudo -n true` | `sudo: a password is required`（rc=1） | **我无法自己改默认路由/DNS**，必须有人输密码 |
| 本机 22 端口 | **closed** | .85 不能反向 SSH 进 Mac 救场，没有第二通道 |
| 默认路由 | `default 192.168.1.1 en1` + `utun4`（Tailscale） | 双默认路由，改错会叠加 VPN 行为 |
| DNS | `192.168.1.11`（**网关是 .1，DNS 却是 .11**） | DNS 已走 .11 的 dnsmasq，S2 结论会被污染 |

更关键的是：**我自己的模型连接走公网**。Mac 一旦没有出口，我不但连不上 .85 的服务器，连"思考"所需的上游 API 都会断，**没有机会执行恢复动作**。所以"我到时再改回来"这个假设不成立。

### 9.2 因此框架的硬性约束（已写进设计）

1. **主框架（S0/S1/S3）永不改任何机器的默认网关**：只在 .85、.11 上各跑本机探针，纯只读。
2. **"客户端视角"不进主框架**，作为可选的受控短测（S2），且必须满足下面全部条件才做：
   - 有人在物理现场或能给出 sudo 密码；我不能独自完成；
   - 用**一次性** `route change default <ip>`（不写入 Wi-Fi 配置，重启/断链自动回退），不用 `networksetup -setmanual`；
   - 一个**分离的 deadman 进程**（`nohup sh -c "sleep 300; 还原" &`，与我的会话无父子关系）到点无条件还原；
   - 脚本开头把基线（gateway/DNS/service order）写进 `logs/stability/pre-s2-baseline.txt`，结束 diff 校验并打印；
   - 探针结果**先落本地 JSONL**，不依赖我在线；恢复后直接读文件出报告；
   - 恢复判据：`route -n get default` = 原网关、`ping 1.1.1.1` 通、`curl` 一个公网 URL 200。
3. **更推荐的替代方案（无需动 Mac）**：在 **.85 上用 network namespace 造一个"假 LAN 客户端"** —— veth 对（`hnpc0` ↔ netns 里的一端），netns 内跑探针，用**独立的测试配置目录**（`/tmp/daetest` 之类）让 dae 绑定该 veth。好处：失败只影响这个 netns，我的 SSH（走 ens2）和整机网络都不受牵连，且我能全权回滚。风险：可能与 live dae 的 BPF/netkit 配置冲突，需要先在 `/tmp` 隔离验证，不碰 `/etc/dae`。
4. S4 故障注入同理：只在 .85 上操作（停/起 dae、reload），**永不**在 .11 上改配置；.11 只读。

### 9.3 断网时的"自救"顺序（写给人看，不是给 agent）

1. `sudo route change default 192.168.1.1`（恢复网关）
2. 若 Wi-Fi 配置被改过：`sudo networksetup -setmanual Wi-Fi 192.168.1.101 255.255.255.0 192.168.1.1`
3. `ping 192.168.1.1` → `ping 1.1.1.1` → 打开 `https://192.168.1.11` 确认 LuCI
4. 若仍不通：关闭/重启 Wi-Fi 接口（`sudo ifconfig en1 down && sudo ifconfig en1 up`），或重启 Mac（一次性 route 不会持久化，重启必然回退）
