# tools/netdiag —— 流量路径只读诊断脚本

用途：搞清「到底哪些流量在这台机器上被 dae 代理、代理到哪个节点」。全部**只读**（python3 + 标准库），
不需要 root 之外的东西，也不改任何配置。原本是在 192.168.1.85 上现场排障时写的，2026-10-23 收回仓库。

## 怎么读结果

- **`dae0` 网卡有流量 = 有东西正在被代理**（dae 用 netkit 设备对 dae0↔dae0peer 接管流量，dae0 在 host 侧）。
  `dae0` 增量长期为 0，就说明本机没有任何流量被代理。
- `ss` 看 dae 的出站连接必须带 `-p`（否则看不到 `users:(("dae",...))`），排障时用 `ss -tnip`。
- 同一网段是**单播交换**：本机网卡只能看到「发给本机/本机发出」的帧，
  所以 `flowsniff.py` 抓不到别的设备访问外网的流量，除非它们真的把 .85 当网关。

## 脚本

| 脚本 | 用法 | 作用 |
|---|---|---|
| `flowprobe.py` | `python3 flowprobe.py 10` | 采样 ens2/dae0 计数增量；`ss -tnip` 解析 dae 出站连接，按节点 (IP,端口) 归并字节 |
| `flowsniff.py` | `python3 flowsniff.py 30 ens2` | AF_PACKET SOCK_RAW 被动抓包，按 (客户端,目的,端口) 聚合，标注目的地是否订阅节点 |
| `flowsniff2.py` | `python3 flowsniff2.py 30` | 同上，但分「其他内网设备→外网」/「本机(.85)→外网」两段（A 段未排除 .85，仅作粗看） |
| `flowwho.py` | `python3 flowwho.py 30` | 按客户端 IP 汇总，Top 目的域名/IP，跳过面板与 SSH 端口 |
| `pubip.py` | `python3 pubip.py` | TLS 直连 api.ipify.org 取当前出口公网 IP（代理路径不稳时会超时） |
| `whereami.py` | `python3 whereami.py [--json] [--watch 5] [--via 192.168.1.85] [--no-trace]` | **在任意测试设备上跑**（macOS/Linux 均可，纯标准库）：本机网卡/网关/DNS/VPN 接口、出口 IPv4+IPv6 与归属、境内 vs 境外的 TCP/TLS 时延指纹、traceroute 首跳，最后给出「本机流量从哪儿出去」的中文判定 |


### whereami.py 的判定依据（怎么看出「被代理」）

三条独立线索互相印证，任一条都不单独下结论：

1. **出口 IP 归属**：境外城市（HK/SG/JP/US…）或机房/云厂商（Vultr/Cloud/Amazon/阿里云…）⇒ 大概率不是家宽直连。
2. **时延指纹**：境外目标 TLS 握手中位数 ≥ 境内 3 倍且 ≥300ms ⇒ 走代理线路；
   而**境外目标 TCP 只要个位数 ms、TLS 却要几百 ms** ⇒ 本地有透明代理/拦截在接管出境流量
   （dae tproxy/netkit 的典型特征：TCP 在本机就被「秒接」，真正的握手发生在远端节点）。
3. **路径与本地线索**：traceroute 首跳是不是网关/.85、到 .85:8787 是否可达、有没有 utun/wg 等 VPN 接口、代理环境变量。

注意 traceroute 全 `*` 不代表断网——UDP 探测被防火墙/代理吞掉很常见（本机 macOS 与 .85 都是这样），此时以时延指纹为准。

## 在一台测试设备上验证「它到底走不走 .85」

不用改任何服务器配置，只要在那台设备上跑 whereami.py，分两次对比：

1. **改动前**跑一次，记下出口 IPv4 与归属、境外 TLS 中位数；
2. 把那台设备的**默认网关和 DNS 都指向 192.168.1.85**（手机/笔记本可临时改 Wi-Fi 静态设置，测完改回）；
3. **改动后**再跑一次：出口 IP 应变成节点出口（如 158.247.231.3 / 韩国首尔）、境外 TLS 中位数明显变大、
   并且出现「本地透明代理」那条判定；
4. 想边改边看就加 `--watch 5`，出口 IP 一变就会打 `<== 变化`。

如果只想确认「这台设备和 .85 是不是同一条路」，加 `--via 192.168.1.85`。


> **IPv6 出口取不到是预期的**：所用机场（订阅上游）没有 IPv6 出口，任何经代理的 IPv6 流量都会失败。
> 脚本会照样报出「无/取不到」，看到这一行不用当故障查。（2026-10-23 确认，用户口径）

## 2026-10-23 用它查出来的结论（详见 architecture.md §14.14）

1. dae 的 `fallback: proxy` + 缺内网直连规则 ⇒ **本机 DHCP(68→67) 与发往 192.168.1.1 的 DNS 被经香港节点代理**
   （journal: `lAddr=192.168.1.85:68 ... proxy_addr=192.168.1.1:67`），面板自身出站也受牵连。
   → 已由面板 `model.EssentialRules` 强制注入内网/本机进程直连规则修复。
2. **没有任何 LAN 客户端经过这台 dae 上网**（45s 抓包中客户端→外网仅 KB 级），
   Mac 的默认网关是 192.168.1.11。要让 LAN 走 dae，必须先解决「谁当网关」，见 §4.4。
3. 订阅节点主机名形如 `<uuid>.bbtechconsultants.com`——之前当成「可疑 DNS 心跳」是误判。
